# 传输进度与交互契约

2026-11-01，设计版本16起的进度契约，对应OpenPencil 09–11页及后续v20双路径修订。

实施进度：SIM-844交付记录（维护者内部验收记录）。P2P接收/任务原子单调确认、独立revision/sample time、双进度快照、接收者route epoch、CLI合并采样和回执保护已实施并部署staging。当前入口为GET /v1/p2p/{id}/progress；完整通用transfer投影、云预上传/引用GC、Web/Flutter v20界面和动效仍待后续单元，不能将本文所有提案视为已实现。

v19 的 [中继预上传契约](relay-preupload.md)补充独立的上行与下行进度段：Cloud 上行封存100%不等于Delivered；接收同意后，下行按接收方自己的确认字节计算。既有流光与真实进度约束继续适用。

v20的[直连与中继送达契约](direct-relay-delivery.md)明确：直连与在线中继共用接收端确认进度和最终回执条件；Cloud节点仅用于实际云上传/云端接收。delivery_progress、spool_progress与route分开投影，DIRECT↔RELAY路径迁移保持同一接收账本和蓝线边界。

## 展示边界

主界面保留两个设备节点和一条 3px 曲线。蓝色 `#0866FF` 表示同一次尝试中已确认接收的字节，灰色 `#EBEBEB` 表示尚未确认的字节。蓝色从发送端沿曲线向接收端增长，接收方向反转路径起点。不能用参数 t 的比例代替曲线弧长比例。

百分比、文件名、字节数、速度、剩余时间、暂停和取消仅出现在详情中：桌面 modal、手机 bottom sheet。点击曲线或任一正在传输的节点打开；曲线指针命中宽度 24px，键盘通过原生节点按钮打开同一详情。关闭详情不暂停、不取消任务。18 版以 16px 节点徽标及提示表达 `Paused`、`Reconnecting`、`Confirming delivery` 等常规状态；需要用户处理的错误在详情保留简短原因与下一步。

蓝线不循环、不前后摆动。视觉弧长为 `acknowledged_bytes / total_bytes`；≤180ms 追到最新样本，不能超过已确认值。减少动态时直接更新弧长。页面隐藏停止过渡，恢复时重新取权威快照。

RUNNING 的活动感由蓝色内部一段柔和高光提供：1600ms 沿发送方向移动，宽度 3px、长度最多为路径的 6%，严格裁切在已确认的蓝色弧长内。它不移动蓝灰分界点，也不进入剩余灰线。暂停时 80ms 淡出并停住，继续时 120ms 淡入；确认、终态、隐藏、未知总量或减少动态时没有此高光。活动动画由前台观测的新鲜度约束，不能在数据面已停滞时继续假装有字节流动。

## 当前实现发现的缺口

| 位置 | 当前事实 | 对体验的影响 |
|---|---|---|
| `backend/internal/service/tasks.go:ReportTaskProgress` | 直接覆盖字节数；不更新独立进度序号 | 乱序回包可能让蓝线倒退，同一状态版本无法排序进度 |
| `backend/internal/service/p2p.go:UpdateP2PProgress` | `GREATEST` 保持 transfer 字节数递增，但没有推进关联 DOWNLOAD task | 任务投影可能一直显示 0%，与 transfer 快照不一致 |
| 同上 | 读权限和接收者检查后，更新不限制 ACCEPTED / RUNNING | 取消、暂停、终态与迟到上报可能交错 |
| `cli/internal/p2p/transfer.go:receiveFrame` | 每个 64KiB 帧同步调用进度 API | 控制面 RTT 阻塞数据面，快速局域网尤其明显 |
| `cli/internal/cmd/upload.go:uploadMissingChunks` | 按当前 chunk 的末尾 offset 上报 | 并行/乱序分块扩展后不能代表去重后的真实确认总量 |
| `backend/internal/service/projection.go` | 任务投影缺少进度采样时间、序号及传输方向 | 无法区分过期进度，DOWNLOAD 的显示叙事也不完整 |
| `backend/internal/service/tasks.go:ControlTask` | 任务由 owner/device 所有者控制；P2P 下载任务属于接收者 | 发送端不能直接拿接收者 task id 调用暂停，不能靠放宽任意 task 权限解决 |
| `web/src/routes/tasks.tsx` | 3s 轮询任务和 transfer，按 task 计算百分比 | 主图更新延迟；两种来源可能表达不同进度 |
| CLI 上传及 P2P 创建 | size/progress 当前均为密文字节；明文大小留在加密 manifest | 不能把明文总大小和密文已确认量混算，也不应为显示进度暴露 manifest |

这些缺口适合增加统一进度投影、节流与事务约束。保留 PostgreSQL 权威状态、Outbox/NATS 稳定领域事件和现有生命周期，无需换掉数据面或消息架构。

## 统一快照

新增经过双方授权检查的 transfer 进度视图；已有任务接口保留兼容。上传/下载 task、P2P 接收确认和云封存通过同一个投影适配，不能在 UI 任意选较大的数。

示意返回体（设计契约，当前 API 尚未提供）：

```json
{
  "transfer_id": "transfer-uuid",
  "attempt_id": "attempt-uuid",
  "task_id": "task-uuid",
  "direction": "SEND",
  "state": "RUNNING",
  "state_version": 4,
  "progress_revision": 38,
  "sampled_at": "2026-11-01T09:00:00Z",
  "progress": {
    "basis": "CIPHERTEXT_ACKNOWLEDGED",
    "acknowledged_bytes": 320000000,
    "total_bytes": 512000000
  },
  "completion": {"verified": false, "delivered": false, "stored": false},
  "capabilities": {"pause": true, "resume": false, "cancel": true}
}
```

- `state_version` 继续参与暂停/继续/取消的乐观锁；`progress_revision` 独立单调递增，不因频繁字节上报导致控制动作持续冲突。
- 快照必须原子读取状态、进度和完成事实。客户端先判断 `attempt_id` 和状态版本，再判断进度序号；相同尝试内只接受更新且不倒退的确认量。终态优先于迟到的活动上报。
- `sampled_at` 表示最后一次有效字节观测的时间；不能用普通轮询响应时间或状态编辑时间冒充。客户端使用接收样本的单调时间计算速率，不比较两端系统时钟。
- 已知总量为非负整数；未知为 `null`，不能用 0 同时代表未知与空文件。未知时曲线保持中性灰，详情显示已接收量，不提供百分比和 ETA。
- 第一版统一使用密文确认字节及密文总量；详情的 MB 定义为十进制。原始文件大小如需显示，应来自客户端解密的 manifest，另设字段，不参与此分数。
- `direction` 对当前查看者计算。`completion` 来自真实校验、封存和送达事实，不由进度或动画推出。
- 能力由服务端按角色及状态计算，客户端只展示可用操作。验证中可关闭详情；暂停/取消是否仍可用必须由快照决定。

## 确认量与控制

1. 上传以对象存储确认并记录的唯一分块长度之和为准，重复块不重复计数；提交分块及推进确认量必须保持一致。不能上报最远 offset 代替累计确认量。
2. P2P 由接收端发布已写入并可恢复的连续分块确认量；直连和中继共用恢复账本。切路径保持同一 transfer/attempt，不重置蓝线。缓冲区写入、发送端排队和网络重传不算确认量。
3. P2P 确认量、关联任务进度与 revision 在同一事务更新，且只允许有效接收者、ACTIVE 授权、ACCEPTED transfer 和 RUNNING task 推进。迟到重复样本幂等，暂停/终态样本返回当前快照。
4. 分块接收不等待每帧 HTTP 上报。内存累计后约 500ms 合并一次，最后一批立即刷新；状态变化及时刷新。后台进度请求必须有超时与取消。进度采集失效不伪造传输失败，但完成前必须核对最终确认量与状态。
5. 控制在 transfer 权限边界内提供给双方，复用现有任务状态机；双方暂停的授权、幂等命令和终态竞争要有测试。不能让发送者获得接收端其他任务的操作权。操作提交中防重复，收到服务端结果后更新状态。
6. 同一尝试暂停/重连后保留确认量，重新收集速率样本。FAILED 重试创建新 attempt；若恢复账本/本地文件丢失导致确认量不可信，也新建尝试并明确反馈，不能一边冻结旧进度一边假装续传。

## 更新通道

本机 UI 可订阅本机数据面样本；跨端通过统一快照约 1s 刷新（仅当前活跃传输，窗口隐藏降低频率）。前台恢复、重连、状态事件到达后立即校准快照。后续若采用 SSE/WebSocket，沿用同一 schema、序号及恢复语义，不把连接是否成功等同于字节正在流动。

高频进度是可丢弃观测，不逐块写 Outbox / JetStream。状态、完成回执和取消仍走可靠事务事件。终态快照需可重读；订阅断线后以权威快照修复。

## 速率、ETA 与完成

- 详情按 3–8s 活跃样本窗口估算速率；刚开始、样本不足、暂停、重连、确认中或超过 3s 未收到有效观测时隐藏速度/ETA。变化剧烈时保留速度、隐藏 ETA，避免来回跳动的倒计时。
- 多文件使用唯一文件的确认字节总和 / 总字节总和；不能平均各文件百分比。未知总量文件存在时，整体也保持未知，不能跳过它们来显示假 100%。每个文件仍有独立尝试和完成事实。
- 字节达到总量时蓝线可以完整，但状态为校验/确认，不能显示送达勾。完整校验及有效接收回执到达后显示 Delivered / Received，并让曲线在 180ms 内淡出。
- 云上传封存仅显示 Stored in cloud，不是 Delivered。缓存命中仍须授权、manifest 校验和引用提交，不能播放假的字节增长过程。
- 已知 0 字节仍经过校验/提交；确认前不计算分数或出现 NaN，完成后详情显示 100%。加密空文件通常仍含协议开销，此时按其实际密文总量正常计算。

## 实施验收条件

乱序、重复、越界、暂停和终态迟到上报不能使确认量倒退或破坏状态；P2P transfer/task 投影一致。双端权限隔离、控制并发、恢复账本丢失、直连/中继切换、空文件、未知总量、批量聚合、云封存与接收回执都需覆盖。

数据面在高 RTT/快速网络下不因逐帧控制 API 被串行限速。实际实现完成后必须按项目约定推送、部署 staging、用真实文件双端冒烟并记录版本和证据；本轮静态与交互设计验证不能替代该验收。
